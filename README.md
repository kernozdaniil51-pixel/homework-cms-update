# homework-cms-update
# RFC / Change Request: Обновление CMS учебного сайта

## 🎯 1. Цель изменения
**Обновление текущей версии CMS** (например, WordPress c версии 6.1 до 6.5) на учебном сайте для устранения уязвимостей безопасности, оптимизации скорости загрузки страниц и получения доступа к новым инструментам редактора.

---

## ⚠️ 2. Риски и их минимизация

| Описание риска | Вероятность | Влияние | Меры по минимизации / Предотвращение |
| :--- | :---: | :---: | :--- |
| Несовместимость текущей темы или плагинов с новой версией CMS | Высокая | Высокое | Предварительное тестирование на тестовом сервере (Staging), обновление плагинов до начала апгрейда ядра. |
| Сбой базы данных во время выполнения скриптов миграции | Низкая | Критическое | Создание полной резервной копии (дампа) БД непосредственно перед началом работ. |
| Нарушение верстки или функционала ключевых страниц | Средняя | Среднее | Тестирование отображения интерфейса сразу после апгрейда по чек-листу. |

---

## 📋 3. План работ (Deployment Plan)

### Предварительные шаги
- [ ] Создать полную резервную копию всех файлов сайта.
- [ ] Создать дамп базы данных (SQL).
- [ ] Проверить работоспособность резервной копии на тестовом окружении.

### Основной этап (Продакшн)
- [ ] Включить режим обслуживания (Maintenance mode) для пользователей сайта.
- [ ] Запустить процесс автоматического или ручного обновления CMS.
- [ ] Обновить установленные плагины и активную тему до актуальных версий.
- [ ] Отключить режим обслуживания.

### Верификация (Проверка)
- [ ] Проверить доступность главной страницы и панели администратора.
- [ ] Проверить корректность работы базы данных (отсутствие ошибок 500).
- [ ] <details><summary>🔍 Развернуть детальный чек-лист проверки функционала</summary><ul><li>[ ] Проверить форму авторизации пользователей.</li><li>[ ] Проверить корректность отображения медиафайлов в галерее.</li><li>[ ] Отправить тестовую заявку через форму обратной связи.</li></ul></details>

## 🔄 4. План отката (Rollback Plan)

Если в процессе верификации обнаружены критические баги, которые невозможно исправить на месте за 15 минут, выполняется полный откат к исходному состоянию:

1. **Включение заглушки:** Активация режима обслуживания.
2. **Восстановление файлов:** Удаление поврежденной директории CMS и извлечение стабильной версии файлов из бэкапа.
3. **Восстановление БД:** Очистка текущей базы данных и импорт предпроизводственного SQL-дампа.
4. **Проверка:** Повторный запуск базовых тестов для подтверждения того, что сайт работает на старой версии CMS.

# 📝 Развернутый ответ: Зачем документировать изменения?

Документирование изменений (Change Management & Documentation) — это фундаментальный процесс в сфере системного администрирования, DevOps и разработки ПО. Он необходим по нескольким ключевым причинам:

1. **Минимизация простоев и рисков (Risk Mitigation):** 
   Если после внесения изменений система «упала» или начала вести себя некорректно, наличие подробного плана работ и плана отката позволяет дежурному инженеру мгновенно вернуть систему в стабильное состояние, сокращая финансовые и репутационные потери бизнеса.

2. **Прослеживаемость и аудит (Traceability & Accountability):** 
   История изменений дает четкий ответ на вопросы: **кто**, **когда**, **что** и **зачем** изменил. Это критически важно при поиске первопричин плавающих багов (Root Cause Analysis), а также для прохождения сертификаций по безопасности (например, ISO 27001).

3. **Снижение «фактора автобуса» (Bus Factor) и обмен знаниями:** 
   Если инженер, настроивший сервер или обновивший CMS, уйдет в отпуск или уволится, команда не останется в неведении. Задокументированные шаги позволяют любому другому квалифицированному специалисту беспрепятственно продолжить поддержку инфраструктуры.

4. **Ускорение диагностики инцидентов:** 
   Вместо того чтобы тратить часы на выяснение причин внезапной поломки, администраторы могут заглянуть в журнал изменений (Changelog / RFC) и сразу увидеть, какое именно обновление или конфигурационный файл правились последними.
